# Контекст проекта: Агрегатор сиделок для животных "Зоопортал"

## Стек технологий
* Бэкенд: Python, Flask
* База данных: SQLite + Flask-SQLAlchemy
* Авторизация: Flask-Login, Werkzeug (хеширование)
* Подтверждение email: `itsdangerous` (подписанные ссылки), `smtplib` (SMTP, stdlib)
* Фронтенд: Чистый HTML/CSS (без фреймворков), шаблонизатор Jinja2 для динамического вывода данных

## Продуктовая логика (две связанные части)
Сайт держится на двух сущностях, и они должны «встречаться» в одном сценарии:

1. **Каталог ситтеров** — публичная часть, доступна без регистрации.
2. **Ветпаспорт питомца** — приватная часть, живёт в личном кабинете владельца.

Связка: владелец выбирает ситтера → передаёт ему карточку питомца → ситтер приходит подготовленным.
Поэтому на главной всегда есть переход «Заполнить ветпаспорт» (в кабинет, а для гостя — в регистрацию),
а в кабинете — обратный переход «Найти ситтера».

## Карта страниц

На них ссылаются шапка, подвал и внутренние CTA — при добавлении секции обновляйте и там, и там.

## Заявки (Request)
Один экран `/request/<kind>` и одна таблица на три сценария:

* `care` — «Запросить уход» на карточке ситтера. Заявка привязана к конкретному специалисту
  (`sitter_slug`, `sitter_name`) и, если пользователь вошёл, к его питомцу (`pet_id`) — ситтер получает ветпаспорт.
* `sitter` — «Подать заявку» из блока для специалистов и из шапки. Обязателен район работы.
* `concierge` — форма на главной (`#contact`) и на `/request/concierge`, когда фильтров каталога
  недостаточно. Гость описывает питомца текстом, авторизованный может приложить ветпаспорт
  (`pet_id`) — в заявку попадёт его снимок, как и у `care`.

Правила:
* гость может отправить заявку, но без `pet_id`; после регистрации с тем же email заявки
  автоматически привязываются к новому аккаунту (`Request.query.filter_by(email=..., user_id=None).update(...)`);
* `pet_id` принимается только из питомцев текущего пользователя и только у `care` / `concierge`,
  чужие id и `pet_id` в анкете `sitter` игнорируются;
* у `care` питомец обязателен: либо `pet_id` из ветпаспорта, либо текстовое `pet_info` (для гостя).
  Если питомец выбран, в `pet_info` сохраняется снимок карточки — заявка не теряет данные после
  правки или удаления ветпаспорта (`/delete_pet` оставляет `pet_id` ссылкой на удалённую строку);
* для авторизованного форма предзаполняется (`_request_defaults`): `email` из аккаунта,
  `name` / `phone` / `district` и выбранный `pet_id` — из последнего обращения **того же `kind`**.
  Тип учитывается, чтобы район работы из анкеты `sitter` не подставился в заявку клиента.
  Все значения остаются обычными редактируемыми полями, ничего не фиксируется жёстко;
  `message` и `pet_info` не подтягиваются, чтобы не тащить старые даты и уже сохранённый снимок паспорта.
  При ошибке валидации показываются присланные значения, а не подсказки;
* в кабинете заявки видны в секции «Мои заявки»; статусы — `new` / `in_progress` / `done`.
  Оператор меняет их напрямую в SQLite (`UPDATE request SET status = ... WHERE id = ...`),
  отдельного внутреннего экрана в проекте нет.

## Подтверждение email

Политика **жёсткая**: пока адрес не подтверждён, аккаунт не считается авторизованным —
входа в кабинет нет (`load_user` возвращает `None`, `@login_required` уводит на `/login`).
Гость по-прежнему может отправлять заявки без аккаунта.

Сценарий:
1. `/register` проверяет формат (`_is_valid_email`: ASCII/punycode, без пробелов, двойных точек,
   нескольких `@` и односимвольных TLD), создаёт `User.email_confirmed = False`, привязывает
   гостевые заявки с тем же email и **не** логинит пользователя.
2. `_issue_confirmation()` строит подписанную ссылку `/confirm-email/<token>` через
   `itsdangerous.URLSafeTimedSerializer` (в payload `uid` + `email`, срок жизни 24 часа).
   Токены в БД не хранятся, поэтому отдельная таблица и чистка просроченных ссылок не нужны.
3. Письмо уходит через `smtplib` (`_send_confirmation_email`). Повторная отправка —
   POST `/confirm-email/resend`, не чаще раза в 60 секунд (`email_confirm_sent_at`).
4. `/confirm-email/<token>` проверяет подпись, срок и совпадение email, выставляет
   `email_confirmed` / `email_confirmed_at` и отправляет на `/login`. Повторный переход
   по ссылке безопасен (идемпотентно).
5. Если кто-то зарегистрировался с чужим неподтверждённым адресом, повторная регистрация
   с этим email обновляет пароль и шлёт новое письмо — адрес не «залипает» за чужим аккаунтом.

Настройки (переменные окружения):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SECRET_KEY` | dev-ключ в `app.py` | подпись сессий и ссылок; **обязательно задать в продакшене** |
| `DATABASE_URL` | `sqlite:///maison_patte.db` | строка подключения |
| `APP_BASE_URL` | — | публичный адрес сайта за обратным прокси (например `https://zooportal.ru`); подставляется в ссылку письма |
| `SMTP_HOST` | — | без неё включается dev-режим |
| `SMTP_PORT` | `587` | порт SMTP |
| `SMTP_SECURITY` | `starttls` | `starttls` / `ssl` / `none` |
| `SMTP_USER`, `SMTP_PASSWORD` | — | логин на SMTP-сервере |
| `SMTP_FROM` | `SMTP_USER` или `no-reply@zooportal.ru` | адрес отправителя |
| `EMAIL_DEV_MODE` | `0` | принудительно включить dev-режим даже с настроенным SMTP |

**Dev-режим**: если `SMTP_HOST` не задан, письмо не отправляется, абсолютная ссылка пишется
в лог (`[DEV] Подтверждение email для ...`), а на `/confirm-email` появляется компактный блок
с короткой ссылкой и кнопкой «Подтвердить email». Ссылка **относительная** — не зависит от `Host`
и `X-Forwarded-Proto`, поэтому работает и локально, и за preview-прокси; сырой токен на экран
не выводится (длинная неразрывная строка распирала бы карточку `.auth-card`). В продакшене
блок не показывается, а для письма используйте `APP_BASE_URL`, иначе Flask подставит внутренний адрес.

**Миграция**: `db.create_all()` не добавляет колонки в уже существующую таблицу `user`, поэтому
при старте выполняется `_ensure_email_confirmation_columns()` (идемпотентные `ALTER TABLE`).
Аккаунты, существовавшие до внедрения подтверждения, помечаются `email_confirmed = 1` —
иначе все текущие пользователи потеряли бы доступ. Новые регистрации всегда начинаются с `0`.

## Шаблоны: правила наследования
* Все страницы расширяют `templates/base.html` (`{% extends 'base.html' %}`).
* В `base.html` живут: `<head>`, шапка с навигацией, flash-сообщения, `<main>`, подвал, скрипт мобильного меню.
* В дочерних шаблонах переопределяются `{% block title %}`, `{% block content %}`, при необходимости — `{% block scripts %}`.
* **Нельзя** копировать шапку/подвал в новую страницу: расхождения между копиями — основная причина, по которой старая версия «расползалась» (разные якоря, разные email).
* Шапка зависит от авторизации: гостю — «Войти / Создать аккаунт», пользователю — «Мои питомцы» + email + «Выйти».
* Каталог ситтеров живёт в `sitters.py` (`SITTERS`, `SERVICE_LABELS`, `get_sitter`) и читается при каждом
  запросе; в БД он не попадает (таблицы `sitter` нет). Главная рендерит карточки циклом,
  экран заявки ищет специалиста в том же справочнике — поэтому данные о ситтере не дублируются в шаблонах.
* Форма консьержа продублирована: инлайн на главной (`#contact`) и полная на `/request/concierge`.
  Обе шлют POST на `/request` и должны иметь одинаковый набор полей (`name`, `email`, `phone`,
  `district`, `pet_info`, `pet_id`, `message`) — при правках обновляйте оба шаблона.
* Hero-карточка «Ветпаспорт в кабинете» на главной показывает **реальное** состояние кабинета:
  последнего питомца пользователя, либо приглашение его добавить, либо помеченный «Пример» макет для гостя.

## Модели базы данных (SQLAlchemy)

```python
from flask_sqlalchemy import SQLAlchemy
from flask_login import UserMixin

db = SQLAlchemy()

class User(db.Model, UserMixin):
    id = db.Column(db.Integer, primary_key=True)
    email = db.Column(db.String(120), unique=True, nullable=False)
    password_hash = db.Column(db.String(256), nullable=False)
    email_confirmed = db.Column(db.Boolean, nullable=False, default=False)
    email_confirmed_at = db.Column(db.DateTime)      # когда подтвердил
    email_confirm_sent_at = db.Column(db.DateTime)   # защита от спама письмами
    pets = db.relationship('PetPassport', backref='owner', lazy=True)

class PetPassport(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    owner_id = db.Column(db.Integer, db.ForeignKey('user.id'), nullable=False)
    pet_name = db.Column(db.String(100), nullable=False)
    species = db.Column(db.String(50), nullable=False) # вид (собака, кот и т.д.)
    breed = db.Column(db.String(100)) # порода
    birth_date = db.Column(db.String(20)) # дата рождения
    vaccinations = db.Column(db.Text) # прививки

class Request(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    kind = db.Column(db.String(20), nullable=False, index=True)   # care | sitter | concierge
    status = db.Column(db.String(20), nullable=False, default='new')
    created_at = db.Column(db.DateTime, nullable=False, default=datetime.utcnow)
    user_id = db.Column(db.Integer, db.ForeignKey('user.id'))      # может быть пусто (гость)
    pet_id = db.Column(db.Integer, db.ForeignKey('pet_passport.id')) # ветпаспорт: care / concierge
    sitter_slug = db.Column(db.String(80))
    sitter_name = db.Column(db.String(100))
    name = db.Column(db.String(100), nullable=False)
    email = db.Column(db.String(120), nullable=False, index=True)
    phone = db.Column(db.String(40))
    district = db.Column(db.String(120))
    pet_info = db.Column(db.String(200)) # описание гостя или снимок ветпаспорта
    message = db.Column(db.Text)
```

Новая таблица создаётся автоматически при старте (`db.create_all()` создаёт отсутствующие таблицы,
но не меняет существующие — для правки колонок нужна миграция). Три колонки подтверждения
email добавляются в существующую таблицу `user` функцией `_ensure_email_confirmation_columns()`
при каждом запуске; см. раздел «Подтверждение email».

## Ближайшие шаги (что осталось за рамками текущей структуры)
* Справочник ситтеров лежит в `sitters.py` и читается на каждом запросе; если каталог понадобится
  редактировать из интерфейса — вынести его в модель `Sitter` с воспроизводимым seed-скриптом
  (БД в `.gitignore`, на свежем клоне она пустая) и фильтровать запросом, а не JS.
* Заявки видит автор в кабинете, а оператор читает таблицу `request` напрямую в SQLite
  (`instance/maison_patte.db`, `SELECT * FROM request ORDER BY created_at DESC`). Статус меняется
  ручным `UPDATE` — внутренний экран для сотрудника пока не нужен.
* Ветпаспорт хранит только отметку «вакцинирован» — добавить дату вакцинации, клинику и номер чипа (потребуется миграция: `db.create_all()` не меняет существующие таблицы).
* Согласие владельца на передачу карточки конкретному ситтеру — сейчас об этом только текст в интерфейсе.
* Уведомлений о новых заявках нет: оператор сам проверяет `Request.status == 'new'`; при необходимости добавить письмо оператору. Почтовый транспорт уже подключён (`_send_confirmation_email`), но пока используется только для подтверждения email.
* Восстановление пароля и смена email не реализованы: неподтверждённый аккаунт можно перерегистрировать, а подтверждённый привязан к своему адресу. Для смены адреса понадобится повторное подтверждение.
* Проверка формата адреса не обращается к DNS/MX и не гарантирует существование ящика — это делает только переход по ссылке из письма.

## Локальный запуск и тесты

```
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt pytest
.venv/bin/python app.py              # http://localhost:5000
.venv/bin/python -m pytest tests -q
```

База `instance/maison_patte.db` в `.gitignore`, на свежем клоне создаётся при старте.
Тесты задают `DATABASE_URL` на временный файл **до импорта** `app.py`, поэтому рабочую БД не трогают.
